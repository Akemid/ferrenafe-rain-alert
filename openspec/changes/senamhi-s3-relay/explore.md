## Current State

- **Port**: `ports.WarningProvider.fetch_current_warnings(region, now) -> SourceResult[tuple[Warning, ...]]`. `SourceResult = Available(data, fetched_at, notes) | Unavailable(source, reason, detail, observed_at)` (`domain/sources.py`).
- **`UnavailableReason`** (`domain/values.py`): `transport_error`, `timeout`, `bad_status`, `malformed_payload`, `structure_unrecognized`, `no_rows_extracted`, `insufficient_horizon`. No staleness or missing-object reason, so add `STALE_RELAY` (and probably `RELAY_MISSING`). Adding a member is safe: `agent_composer.fallback_reason_for` is total (falls back to `UNEXPECTED_ERROR`); `outage.py` renders `reason.value` generically; `detail` is capped at 160 chars and sanitized.
- **Scraper**: `senamhi_scraper.parse_warnings_page(html, region, now) -> ParseOutcome` is ALREADY a pure function and raises `FetchError(reason, detail)`. `SenamhiWarningScraper` = fetch (injected `HtmlFetcher`) + parse + `parse_notes` + catch-all -> `Unavailable`. `now` is used for the vigente in-force window check. `Available.fetched_at` is today just `now`; it is never used for freshness (only `cli.py` prints it). For the relay it must carry the relay timestamp.
- **Seam**: `HtmlFetcher` Protocol (`fetch(url) -> str`). Smallest-change option: an `S3HtmlFetcher` implementing `HtmlFetcher` that raises `FetchError(STALE_RELAY, ...)`, reusing `SenamhiWarningScraper` unchanged. Catch: `fetched_at` would equal `now` (loses the relay timestamp) and the `url` argument is ignored (like `FileHtmlFetcher`). Cleaner: `RelayWarningProvider(reader, max_age)` composing `parse_warnings_page` directly, setting `Available.fetched_at` = relay time. Recommend the latter, sharing `parse_notes`; maybe add a note "relay age Xh" to `Available.notes`.
- **`wiring.py`**: `build_cloud_deps()` takes no args and hardwires `SenamhiWarningScraper(HttpxHtmlFetcher())`. Env-selection precedent: `select_snapshot_publisher(env: Mapping)` reads `RAIN_ALERT_SNAPSHOT_BUCKET`/`KEY`. Add `select_warning_provider(env)` in `wiring.py`: if `RAIN_ALERT_RELAY_BUCKET` is set -> relay provider; else direct scraper (keeps local/CLI behaviour; `build_local_deps` untouched). To decide: a relay env var that is set but misconfigured must fail toward `Unavailable`, not silently fall back to direct scraping? (A direct scrape from AWS just times out in 3 s: harmless but noisy.)
- **S3 adapter style**: `s3_snapshot_publisher.py`: lazy boto3 client with explicit `Config(connect 3s, read 5s, total_max_attempts=2)`, client injected as `Any`, env var constants in the module. Tests: hand-written `FakeS3Client` in `tests/unit/adapters/test_s3_snapshot_publisher.py` (local to the file; `tests/support/fakes.py` has no S3 fake). A relay reader needs a fake `get_object` returning `{"Body": file-like, "LastModified": datetime, "Metadata": {...}, "ContentLength"}` and raising botocore `ClientError` (`NoSuchKey` / `AccessDenied`) — construct a real `ClientError`, no mock. There is also a test pinning that `_resolved_client` builds a bounded `Config` (monkeypatch `boto3.client`) — copy the pattern. Existing fakes: `FakeWarningProvider` (`fakes.py:80`), `build_fake_deps` in `tests/support/wiring.py`.
- **Infra**: the `PublicSnapshotStack` bucket has block-public relaxed (`blockPublicPolicy=false`, `restrictPublicBuckets=false`) because Amplify reads unsigned; `GetObject` is granted to `AnyPrincipal` on `status.json` only; `SnapshotWriter` managed policy = `PutObject` on `status.json`; versioned; `autoDeleteObjects` deliberately off. Reusing it for relay input is NOT recommended: the policy is per-key so the relay object would not be public today, but the bucket's relaxed guards mean one wrong statement exposes it, and it mixes the resident-readable output with an untrusted-input path and a producer `PutObject` credential next to the page's own object. Recommend a NEW private bucket (`BlockPublicAccess.BLOCK_ALL`, `enforceSSL`, versioned, SSE-S3, lifecycle expiry of noncurrent versions ~30 d), in `ScheduledCycleStack` or a small `RelayStack`. The name should not embed the account id (hygiene test): let CDK generate it or pass it via `-c` like `snapshotBucketName`; Lambda env `RAIN_ALERT_RELAY_BUCKET`. Lambda role: `s3:GetObject` on exactly `senamhi/latest.html` (ARN of one key). Note `ExecutionRole` has no managed policies; grants are added explicitly. If the bucket is versioned and only latest is read, no `GetObjectVersion` is needed. Producer: separate managed policy `RelayWriter` = `s3:PutObject` on one key (no Delete, no List), mirroring `SnapshotWriter`. Infra tests live in `infra/test/scheduled-cycle-stack.test.ts` (assert on the synthesized template).
- **Schedule**: EventBridge Scheduler `cron(0 0,6,12,18 * * ? *)` America/Lima, i.e. every 6 h; `maxEventAge` 1 h, `retryAttempts` 2; alarm: `NoInvocations` over 8 h. Lambda timeout 120 s, 512 MB; the SENAMHI page (~512 KB) parses fine in memory. The HTTP side has no retries by design (D12).
- **Producer side**: no reusable fetch-only SENAMHI CLI exists. `rain-alert-cycle` (`entrypoints/cli.py:main`) runs the whole cycle with `ConsoleNotifier`; `build_local_deps` uses `HttpxHtmlFetcher` + `warnings_url_for(region)` (`senamhi_scraper`). The producer can reuse `warnings_url_for` + `HttpxHtmlFetcher` (3 s/5 s timeouts, `FetchError`). Minimal producer: a new entrypoint `rain-alert-relay-push` (`pyproject [project.scripts]`) = fetch HTML, optionally parse with `parse_warnings_page` as a gate (refuse to upload a page that does not parse), `PutObject` body + `Metadata{fetched-at ISO UTC, sha256}`, then a launchd plist (`StartInterval` ~1800–3600 s) in `docs/runbooks` or `ops/`. launchd on a sleeping laptop skips runs, so staleness is expected; a Raspberry Pi later removes this.
- **Credential options for the unattended producer** (tradeoffs; unverified against docs — not fetched):
  - (a) IAM user + access key limited to `PutObject` on one key: simplest, works with boto3 env/profile, but a long-lived secret on a Mac that needs rotation discipline; blast radius = inject HTML (see risk).
  - (b) IAM Roles Anywhere: short-lived credentials from an X.509 cert via `aws_signing_helper` `credential_process`; no long-lived AWS secret, but needs a CA/trust anchor + cert lifecycle; overkill for one Mac.
  - (c) Presigned-URL issuer: the cycle Lambda or another service mints a short-lived presigned PUT for the producer; needs a way to deliver URLs to the producer; adds an auth surface; poor fit for unattended use.
  - (d) `aws login`: expires — already rejected.
  - Recommend (a) for v1 with a dedicated IAM user, key stored in macOS Keychain, and a rotation/last-used check in the runbook; revisit (b) when the Pi arrives.
- **Freshness**: use S3 `LastModified` (server clock, not forgeable by the credential holder except by re-PUT) as the authoritative timestamp; the producer-claimed `fetched-at` metadata is informational and should be cross-checked (reject/flag if `|claimed - LastModified| > ~15 min` or claimed in the future). The threshold must exceed producer interval + sleep tolerance and should relate to the 6 h schedule: with an hourly push, a 3–4 h threshold tolerates a few missed pushes; a threshold >= 6 h means a cycle can run on data from the previous cycle's window (acceptable only if product agrees). Make the threshold a module constant/env, tested at the boundary (age == max is stale or fresh: pick and pin).
- **Risks**:
  1. Trust boundary — the credential holder can inject HTML; the worst case is a forged calm page -> `Available(empty)` -> the evaluator takes the forecast-only STRICTER 70% branch, i.e. LESS sensitive than `Unavailable` (same defect class as the `senamhi_scraper` docstring). Mitigations: scoped credential, bucket versioning (audit/rollback), producer-side parse gate, the Lambda-side parser already rejects non-table pages and anomalies on the vigente row; consider content sha256 + size cap; note in an ADR that integrity = credential secrecy (no signature scheme).
  2. A dead/slept relay must be `Unavailable(stale)`, never `Available` — and the heartbeat is the schedule; add tests for missing key, stale, future-dated, empty body, oversized body.
  3. The producer must NOT push when its own fetch/parse fails (otherwise it refreshes `LastModified` over bad content and a stale-good object gets replaced by garbage); conversely a fetch failure should leave the old object to age out.
  4. Size: cap the read (`ContentLength` check, e.g. 5 MB vs ~512 KB real) before reading the body; decode as explicit UTF-8 (`httpx .text` uses the response charset — the producer should store bytes + `ContentType` charset; verify the live encoding).
  5. The relay does not make the SENAMHI fetch observable: the operator notice detail will say `stale_relay` — ensure the outage notice distinguishes "SENAMHI down" from "relay stale" (detail text, <= 160 chars).
  6. The Lambda cold path adds S3 call latency/failure; S3 same region, bounded timeouts like the publisher.
  7. The hygiene test scans for 12-digit numbers/ARNs: no account id in bucket names/docs.
  8. Snapshot/public page: check `domain/snapshot.py` for whether it surfaces unavailable reasons to residents (not verified here).
- **Not verified**: `tests/support/wiring.py` contents, `snapshot.py` exposure of reasons, live SENAMHI charset, IAM/Roles Anywhere docs. No openspec write tool was available in the explore executor: engram only. *[transcription note: the original also stated that `openspec/changes/` had no entries; that is incorrect — `scheduled-cycle/`, `composer-agent/` and `archive/` exist.]*

## Approaches

1. **`S3HtmlFetcher` adapter under the unchanged `SenamhiWarningScraper`** — Low effort; loses the relay timestamp in `Available.fetched_at`, staleness expressed via `FetchError(reason)` only.
2. **`RelayWarningProvider` (new `WarningProvider`) = S3 reader port + freshness + `parse_warnings_page`** — Medium; explicit `fetched_at`, notes, testable with a `FakeRelayReader`; RECOMMENDED. Introduce a small port `RelayObjectReader` returning `(html, last_modified)`.
3. **S3-event-triggered cycle** — rejected by design (silence on a dead relay).

## Recommendation

Approach 2, a new private bucket, new reasons `STALE_RELAY`/`RELAY_MISSING`, wiring via `RAIN_ALERT_RELAY_BUCKET` in `build_cloud_deps` only, IAM-user producer for v1.

## Open product questions

1. Freshness threshold vs the 6 h schedule and the acceptable risk window.
2. Who operates/monitors the relay; who is alerted when it dies, and with what response time.
3. What residents are told (if anything) when the relay is stale (the degraded template is already forecast-only) vs an operator-only notice.
4. Is it acceptable to keep alerting in forecast-only mode for days while the relay is down during the rainy season (Dec+)? Escalation path (second producer / Pi)?
5. Is a forged/incorrect relay payload risk acceptable given credential-only integrity?

All five were answered by the owner in the proposal question round; see `proposal.md` → *Business rules*.
