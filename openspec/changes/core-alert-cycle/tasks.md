### Added at the 2026-09-05 security review remediation

- **RESOLVED (HIGH) — a scraped aviso title could forge structure inside the Spanish community message.** `Warning.title` is stored raw and interpolated into a body assembled with `"\n".join`, whose grammar is `- ` bullets and `Motivos:` / `Recomendaciones:` headers. Reproduced end to end: a title carrying newlines produced **two** `Recomendaciones:` sections, the forged one ahead of the genuine one and formatted identically, plus a live ANSI escape and a surviving U+202E override. New `domain/sanitize.py` collapses whitespace runs, strips C0/C1 controls and bidi controls U+202A–U+202E and U+2066–U+2069, trims, and caps at 200 characters with a visible marker. Applied at all four rendering boundaries: `domain/template.py`, `domain/reasons.render_reason_en`, `senamhi_scraper.parse_notes`, and `serialization.reason_to_dict`. The invariant is stated on the `MessageComposer` port so change 2's agent composer inherits it. The title is still stored raw on purpose — sanitizing is a rendering concern, and normalizing on the way in is what once put `EXTENSION` in front of recipients.
- **RESOLVED (MEDIUM) — an uncaught `ValueError` aborted the whole cycle on a malformed forecast value.** `json.loads` accepts bare `NaN` and `Infinity`; `int(float("nan"))` raises `ValueError`, which is not a `FetchError`, and `RunAlertCycle` has no handler, so the run died with a traceback and produced neither an alert nor an operator notice. `Infinity` millimetres was quieter and worse: it parsed as valid, accumulated to an infinite total and cleared `imminent_mm_24h` unconditionally. `_millimetres` and `_percent` now reject non-finite, negative and out-of-range readings; `HourlyPoint.__post_init__` enforces the same ranges where the invariant is claimed; and both `OpenMeteoForecastProvider` and `OfflineOpenMeteoProvider` gained the catch-all the sibling scraper already carried.
- **RESOLVED (LOW) — the `--json` document was not parseable because the notifier shared stdout.** `build_local_deps` now takes a `notifier_stream`, and the CLI passes stderr under `--json`. Verified against the real entry point: a sending run went from `JSONDecodeError` to a parseable document. Three existing tests had been silently working around it by slicing from the first `{`.
- **Open, carried to change 3 — there is no advisory lock on the state file, and two concurrent runs lose each other's records.** Measured, not theorised: two `JsonFileAlertRepository` instances reading before either writes leaves exactly one record on disk. A lost record is a *dedup* record, so the consequence is a community re-alerted for a window already delivered. **A lock around the write would not fix it.** Both writes are already atomic through `os.replace`; the loss is a read-modify-write lost update caused by the second process's stale in-memory snapshot, so the lock must span the first read of a cycle to its last write. **Concrete proposal**: give `JsonFileAlertRepository` a `__enter__`/`__exit__` that acquires an exclusive `fcntl.flock` on a sidecar `<state-file>.lock` opened for the lifetime of the block, invalidates `self._state` on entry so the first read happens inside the lock, and have `cli.main` wrap the `RunAlertCycle(deps).execute()` call in that block. Add a `timeout` so a stale holder degrades to a clear "another cycle is running" message and `EXIT_CANNOT_START` rather than hanging a cron job. Deliberately **not** implemented in this slice for three reasons: `AlertRepository` has no lifecycle in its contract, so this changes either the port or the entrypoint's structure rather than adding a few lines; `fcntl.flock` is POSIX-only, and the project has not decided whether Windows is supported; and change 3 replaces this adapter with DynamoDB, where the correct mechanism is a conditional write on the item, not a file lock, so nothing here would be shared. It is unrealistic for a single-operator CLI run by hand and becomes real the moment a scheduler exists — which is change 3.
- **Considered and rejected — sanitizing the title at the adapter boundary instead of at each rendering boundary.** It would have been one call site rather than four, but `Warning.title` is the record of what SENAMHI actually published, and the field's own docstring records the damage the last normalize-on-ingest attempt did. Sanitizing at four rendering boundaries through one shared domain function keeps one rule and preserves the record.
- **Confirmed — `json.dumps` escaping alone was not enough for the `--json` path.** It escapes control characters but, under this project's `ensure_ascii=False`, writes bidi overrides through verbatim. Three fields (`message.body`, `reasons_en`, `notes`) were already covered by an upstream sanitizing renderer; `reasons[].title` was not, which is why `reason_to_dict` sanitizes. Every field of the document is now covered.
